# 🔒 عضویت اجباری کانال (Force Join) — گزارش فنی، کد و اعداد

نسخه: ۱.۷ — پیاده‌سازی‌شده و آزموده‌شده روی همین مخزن (Foxora)
تاریخ: ۲۰۲۵/۱۱/۰۲

این سند سه بخش اصلی دارد: **گزارش فنی سورس‌محور** (چه چیزی واقعاً وجود دارد)،
**معماری و کدِ پیاده‌شده**، و **اعداد بنچمارک واقعی همراه با محدودیت‌های
صادقانه**. هر جا چیزی آزموده نشده، صریح نوشته شده است «آزموده نشده».

## ۰. خلاصهٔ یک‌صفحه‌ای

| پرسش | پاسخ |
|---|---|
| آیا می‌توان **فقط اعضای جدید و تغییرات عضویت** را گرفت؟ | **تا حد زیادی بله، ولی نه با «delta» سرور.** سروش پلاس نه `channels.getAdminLog` دارد و نه API افزایشی برای اعضا. تنها مسیر «فقط تغییرات» = رویداد `UpdateChannelParticipant` که تحویل زنده‌اش باید روی حساب واقعی تأیید شود. در این patch به رویداد تکیه نمی‌شود: مسیر پیام از کش و پیمایش هدفمند شروع می‌کند؛ اسکن کامل + diff فقط برای همگام‌سازی/گزارش عمدی می‌ماند. `getParticipant` برای رکورد legacy پیش‌فرض خاموش است و فقط بعد از probe موفق صریح فعال می‌شود. |
| فراخوانی API در مسیر گرم (هر پیام) | **صفر** (اندازه‌گیری‌شده: ۱۰۰۰ پیام → ۰ فراخوانی) |
| فراخوانی پس از ری‌استارت | **صفر** (کش `access_hash` از SQLite بازسازی می‌شود) |
| روش ممنوع (کل اعضا در هر پیام) | ۱۲ فراخوانی و ~۱٬۴۹۳ms در هر پیام برای کانال ۲٬۰۰۰ نفره |
| در قطعی API | عضویت تأیید نمی‌شود و پیام حذف نمی‌شود (fail-open) |
| **مهم‌ترین یافتهٔ میدانی (۲ آذر)** | `channels.getParticipant` روی سرور سروش **پیاده نشده است**: `RPCError 422: NOT_SUPPORTED`. پس بررسی عضویت **چندمسیره** شد (§۶.۶) |
| مسیرهای بررسی (به ترتیب هزینه) | `getParticipant` → Bot API `getChatMember` → جست‌وجوی هدفمند عضو → اسنپ‌شات کامل اعضا |
| تست‌ها | ۸۳ تست در `tests/test_force_join.py` — همه پاس |

### ۱.۲ پاسخ به ۹ پرسش الزامی (نام دقیق متد، پارامتر، خروجی، محدودیت)

| # | نیاز | پاسخ واقعی از سورس |
|---|---|---|
| ۱ | فهرست اعضای کانال | `functions.channels.GetParticipantsRequest(channel: InputChannel, filter: TypeChannelParticipantsFilter, offset: int, limit: int, hash: int)` → `channels.ChannelParticipants(count, participants, chats, users)` یا `channels.ChannelParticipantsNotModified`. سقف صفحه در خود کتابخانه: `_MAX_PARTICIPANTS_CHUNK_SIZE = 200` (`client/chats.py:17`). |
| ۲ | اطلاعات یک عضو مشخص با شناسه | همان `GetParticipantsRequest` با `filter=ChannelParticipantsSearch(q='')` (جست‌وجوی هدفمند) **یا بهتر**: `GetParticipantRequest` (ردیف ۳). |
| ۳ | **API مستقیم بررسی عضویت یک کاربر** | `functions.channels.GetParticipantRequest(channel: InputChannel, participant: InputPeer)` → `channels.ChannelParticipant(participant, chats, users)` که `participant` آن یکی از `ChannelParticipant` / `ChannelParticipantAdmin` / `ChannelParticipantCreator` / `ChannelParticipantSelf` (عضو) یا `ChannelParticipantLeft` / `ChannelParticipantBanned` (غیرعضو) است. **نیازمند `access_hash` کاربر** (`participant: TypeInputPeer`) — که `splusthon.utils.get_input_user(user)` بدون RPC می‌دهد. خطای «عضو نیست»: `errors.UserNotParticipantError`. **⚠️ تصحیح ۱.۲:** این متد در Schema هست ولی **سرور سروش آن را پیاده نکرده** و `422 NOT_SUPPORTED` می‌دهد (§۶.۶) — پس «در دسترس بودن در کتابخانه» ≠ «کار کردن روی سرور». |
| ۴ | رویداد ورود عضو جدید به کانال | `types.UpdateChannelParticipant(channel_id, date, actor_id, user_id, qts, prev_participant, new_participant)`؛ `events.ChatAction.build` آن را می‌شناسد (`events/chataction.py`): `new_participant` بدون `prev_participant` ⇒ `user_added`/`user_joined`. |
| ۵ | رویداد خروج عضو | همان `UpdateChannelParticipant`؛ `prev_participant` بدون `new_participant` ⇒ `user_left` (وقتی `actor_id == user_id`) یا `user_kicked`. |
| ۶ | فقط اعضای تغییرکرده از آخرین بررسی | **وجود ندارد.** نه پارامتر زمانی دارد، نه کرسر. تنها «فقط تغییرات» = رویداد ردیف ۴/۵ (شرط: ادمین بودن در کانال). |
| ۷ | Delta / Incremental Updates | **وجود ندارد.** `channels.getAdminLog` در TL Schema سروش نیست (زیر `functions.channels` هیچ `GetAdminLogRequest` نیست؛ `hasattr` روی هر سه کتابخانه `False`). بنابراین `client.iter_admin_log(...)` در عمل با `AttributeError` می‌شکند — با تست `test_schema_evidence_about_library_capabilities` قابل بازتولید است. جایگزین: اسنپ‌شات + diff محلی (بخش ۲.۴). |
| ۸ | تفاوت ربات رسمی و حساب کاربری | حساب کاربری (User-Bot) که **ادمین کانال** باشد هم `getParticipant` می‌گیرد هم `UpdateChannelParticipant`. حساب غیرادمین با کانالِ `participants_hidden=True` به `ChatAdminRequired` می‌خورد. Bot API رسمی (نگاه کنید به `SplusLib.BotClient` و `bot_api_mode.py` همین پروژه) دسترسی به فهرست اعضا **ندارد**؛ تنها `getChatMember` سطحی و `chat_member` update برای ربات‌های ادمین. (پیاده‌سازی نسخهٔ Bot API در این پروژه اضافه شد: `bot_api_get_chat_member`؛ پشتیبانی سرور سروش **آزموده نشده** — با `tools/soroush_membership_probe.py` روی حساب خودتان یک‌بار سنجیده می‌شود.) |
| ۹ | آیا ادمین بودن کافی است؟ | برای دریافت رویدادهای اعضا: **بله، ادمین بودن کانال لازم و کافی است** (سمت سرور، آزموده نشده). برای `getParticipant` روی کانال مخفی: بودن در فهرست ادمین‌ها لازم است. برای فهرست اعضا: `ChannelFull.can_view_participants` و `ChannelFull.participants_hidden` تعیین‌کننده‌اند — هر دو فیلد در `types.ChannelFull` این نسخه وجود دارند (تأیید با `__init__.__code__.co_varnames`). |

### ۱.۳ یافته‌های پیش‌تأییدشده: تأیید یا رد

| یافتهٔ پرامپت | وضعیت | شاهد |
|---|---|---|
| `channels.getAdminLog` در schema نیست، پس `iter_admin_log` کار نمی‌کند | **تأیید** | `hasattr(functions.channels, "GetAdminLogRequest") is False`؛ `iter_admin_log` روی کلاینت هست ولی `_AdminLogIter._init` به `functions.channels.GetAdminLogRequest` ارجاع می‌دهد که وجود ندارد. در NSplusthon 1.8.2 و SplusPy 2.2.12 هم همین‌طور. |
| `UpdateChannelParticipant` هم ورود و هم خروج را می‌دهد | **تأیید** | `events/chataction.py` دستهٔ `UpdateChannelParticipant` را می‌سازد؛ تست با آبجکت واقعی: `user_added` و `user_left` |
| `channels.getParticipant` وجود دارد ولی `access_hash` می‌خواهد | **تأیید** | امضای `GetParticipantRequest(channel: TypeInputChannel, participant: TypeInputPeer)` |
| `getParticipants` با صفحهٔ ۲۰۰ و `hash` پاسخ `ChannelParticipantsNotModified` می‌دهد | **نیمه‌تأیید** | صفحه ۲۰۰: تأیید (`_MAX_PARTICIPANTS_CHUNK_SIZE = 200`). نوع `ChannelParticipantsNotModified` وجود دارد **اما زیر `splusthon.tl.types.channels`** نه `splusthon.types`. همچنین `iter_participants` کتابخانه **همیشه `hash=0`** می‌فرستد، پس این کش عملاً استفاده نمی‌شود. ما هم به آن تکیه نمی‌کنیم. |
| `UserNotParticipant` را از `ChatAdminRequired` جدا کن | **تأیید و پیاده شد** | `force_join_api.classify_error` این دو را به `not_member` و `no_access` نگاشت می‌کند |
| `ChannelFull.can_view_participants` و `participants_hidden` | **تأیید** | در امضای `types.ChannelFull` |

### ۱.۴ محدودیت‌هایی که از سورس بیرون آمد (و طراحی را تغییر داد)

1. `client.get_permissions(channel, user)` هم همان `GetParticipant` است، ولی
   قبلش `get_entity(entity)` و `get_input_entity(user)` صدا می‌زند
   (`client/chats.py:1229-1245`) که می‌تواند RPC اضافه بسازد. ما مستقیم
   `GetParticipantRequest` را با `InputChannel`/`InputPeerUser` **از کش
   SQLite** می‌سازیم.
2. `iter_participants` کتابخانه برای کانال‌های با فیلتر پیش‌فرض یک
   `getParticipants` اضافه (limit=1) هم می‌زند تا `total` را بگیرد؛ ما
   مسیر مستقل و صریح خودمان را داریم تا دقیقاً بدانیم چند فراخوانی
   می‌شود.
3. سقف `200` یعنی کانال ۱۰٬۰۰۰ نفره = ۵۰ فراخوانی برای یک اسنپ‌شات. این
   کار فقط در ناظر دوره‌ای (نه در مسیر پیام) انجام می‌شود و با بودجهٔ
   زمانی و فاصلهٔ RPC محدود است.

### ۲.۲ دیتابیس (SQLite با WAL، از طریق `modules.runtime_db`)

```sql
force_join_groups(
  group_id INTEGER PRIMARY KEY,      -- کلید کانونیک علامت‌دار
  channel_id INTEGER NOT NULL,       -- بدون علامت
  channel_access_hash INTEGER,       -- کش برای صفر-API شدن مسیر گرم/ری‌استارت
  channel_link TEXT, channel_title TEXT,
  force_join_enabled INTEGER DEFAULT 1,
  last_sync_time INTEGER,
  last_update_cursor TEXT,           -- JSON محلی (نه توکن سرور)
  sync_mode TEXT,                    -- event | snapshot | probe
  created_at INTEGER, updated_at INTEGER
)

force_join_members(
  user_id INTEGER, channel_id INTEGER,
  membership_status TEXT,            -- member | not_member | unknown (CHECK)
  last_verified_at INTEGER,
  source TEXT,                       -- event_join | event_leave | rpc | snapshot
  join_date INTEGER, access_hash INTEGER,
  PRIMARY KEY (user_id, channel_id)
)
```

ایندکس‌ها: `(channel_id, membership_status)` و `(channel_id, last_verified_at)`.
`journal_mode=WAL`، `synchronous=FULL`، `busy_timeout=10000`، هر تغییر در یک
تراکنش `BEGIN IMMEDIATE`.

### ۲.۳ مسیر پیام (تا حد امکان ارزان)

```
پیام گروهی می‌رسد
 ├─ قابلیت برای گروه فعال است؟        → فقط dict lookup (کش منفی هم دارد)
 ├─ فرستنده معاف است؟                  → مالک ربات/مالک گروه/ادمین ثبت‌شده/
 │                                        ادمین واقعی/VIP/ربات/پست کانالی
 ├─ پیام فقط‌رسانه‌ای هم از همین دروازه رد می‌شود (پس از معافیت‌ها)
 ├─ کش حافظه (TTL عضو ۳۰د / غیرعضو ۵د) → تصمیم، صفر I/O
 ├─ SQLite (همان TTL)                  → تصمیم، صفر RPC
 └─ حداکثر یک RPC: channels.getParticipant
        ├─ member      → پیام می‌ماند
        ├─ not_member  → حذف + پیام راهنما (با محدودیت نرخ)
        └─ unknown/خطا → **پیام حذف نمی‌شود** (fail-open) + لاگ
```

الزامات اجراشده:

* **single-flight**: `_inflight[(channel,user)]` — همهٔ درخواست‌های هم‌زمانِ
  یک کاربر یک Future مشترک را `await` می‌کنند (تست:
  `test_single_flight_dedupes_identical_concurrent_requests`، ۲۵ درخواست
  هم‌زمان → **۱** فراخوانی).
* **سقف هم‌زمانی**: `asyncio.Semaphore(FORCE_JOIN_MAX_CONCURRENCY=2)`.
* **fail-safe**: در `TimeoutError`/خطای شبکه/`ChatAdminRequired` وضعیت
  `unknown` است و پیام حذف نمی‌شود.
* **grace زمان‌دار**: شاهد تازهٔ «غیرعضو» (≤ ۶۰۰ ثانیه) در قطعی هم اجرا
  می‌شود؛ «عضو» تا ۲۴ ساعت پذیرفته می‌شود؛ بعد از آن «نامعلوم» = آزاد.
* **کنترل نرخ پیام راهنما**: cooldown ۶۰۰ ثانیه برای هر کاربر + سقف ۲۰ در
  دقیقه برای هر گروه + حذف خودکار پیام راهنما با `notice_cleanup` موجود.

### ۲.۴ لایه‌های جبرانی تشخیص خروج (چون کش می‌تواند کهنه شود)

| لایه | چه چیزی را می‌گیرد | هزینه |
|---|---|---|
| رویداد `UpdateChannelParticipant` | خروج/اخراج فوری، باطل‌سازی **دیتابیس + کش حافظه** | صفر |
| TTL کوتاه برای «غیرعضو» و TTL ۳۰ دقیقه‌ای برای «عضو» | خروج‌های بی‌رویداد در بازهٔ چند دقیقه | یک RPC برای هر کاربر در هر TTL |
| اسنپ‌شات دوره‌ای + diff محلی | خروج‌های بی‌رویداد (مثلاً هنگام خاموش بودن ربات) | یک‌بار هر ۶–۱۲ ساعت، صفحه‌ای |
| **قاعدهٔ سخت** | اگر اسنپ‌شات **ناقص** بماند (بودجه تمام شود/خطا/سقف)، هیچ عضوی «خارج‌شده» ثبت نمی‌شود | — |

اسنپ‌شات فقط ردیف‌هایی را «خارج‌شده» می‌کند که `last_verified_at <=
snapshot_started_at` باشند؛ بنابراین رویداد ورودِ تازه با دادهٔ کهنهٔ اسنپ‌شات
باطل نمی‌شود.

### ۲.۵ ثبت کانال = **سنجش واقعی**، نه حدس

فرمان «کانال من …» این کارها را می‌کند:

1. resolve با `get_entity` (یک RPC) و گرفتن `access_hash` + عنوان + لینک.
2. `GetFullChannelRequest` → `can_view_participants`، `participants_hidden`،
   `participants_count`.
3. سنجش **هر چهار مسیر** (`probe_access`، جدول §۶.۶):
   * `getParticipant` روی حساب خودمان؛
   * Bot API `getChatMember` (اگر `BOT_TOKEN` هست)؛
   * `getParticipants(recent, limit=1)` — آزمون خواندنی بودن فهرست؛
   * `getParticipants(ChannelParticipantsAdmins)` — تشخیص ادمین بودن حساب
     **بدون** `getParticipant` (چون آن متد روی سروش نیست).
4. ذخیرهٔ نتیجهٔ سنجش در کرسر گروه (`routes`) — بررسی بعدی هیچ‌گاه مسیر
   مرده را دوباره صدا نمی‌زند.
5. انتخاب `sync_mode`:
   * ادمین + فهرست خواندنی ⇒ `event` (رویدادمحور، هزینهٔ صفر)
   * غیرادمین + فهرست خواندنی ⇒ `snapshot`
   * فقط Bot API ⇒ `bot_api`
   * هیچ مسیری ⇒ `probe` و **قابلیت فعال نمی‌شود** (با پیام صریح)
6. «تنظیم عضویت اجباری» هم اگر مسیری نداشته باشد، سنجش دوباره می‌کند و در
   نبود مسیر، فعال‌سازی را رد می‌کند (`enable_channel` → `probe_access`).

تحمل نوشتاری: «ي/ك» عربی، «ى/ئ»، نیم‌فاصله (`\u200c`)، فاصله‌های اضافه،

## ۶. محدودیت‌های صادقانه (چه چیزی کار نمی‌کند و چه هزینه‌ای دارد)

1. **Delta سرور وجود ندارد.** بدون ادمین بودن در کانال، «تشخیص فوری خروج»
   ممکن نیست و به TTL + اسنپ‌شات تکیه می‌کنیم. بدترین حالت: کاربری که خارج
   شده تا TTL «عضو» (پیش‌فرض ۳۰ دقیقه) می‌تواند پیام بدهد. برای سخت‌گیری،
   `FORCE_JOIN_MEMBER_TTL` را کم کنید (هزینه: RPC بیشتر).
2. **رویدادهای اعضای کانال فقط به ادمین کانال می‌رسد.** اگر حساب ربات ادمین
   نباشد، حالت به `snapshot` یا `probe` تنزل می‌کند (هزینهٔ بیشتر یا دقت کمتر).
3. **کانال با فهرست اعضای مخفی** (`participants_hidden=true`) و بدون ادمین
   بودن: `getParticipant` هم `ChatAdminRequired` می‌دهد؛ در این حالت قابلیت
   **عمداً فعال نمی‌شود** تا پیام کاربران واقعی حذف نشود.
4. **`access_hash` می‌تواند باطل شود** (تغییر اکانت، حذف/ساخت دوبارهٔ کانال).
   در این حالت یک resolve خودکار انجام و کش نو می‌شود؛ اگر شکست بخورد
   fail-open می‌شود.
5. **`getParticipants` ۲۰۰ نفر در هر صفحه** است؛ کانال ۱۰٬۰۰۰ نفره = ۵۰
   فراخوانی در هر اسنپ‌شات (فقط در ناظر، با فاصلهٔ ۰٫۳۵ ثانیه ≈ ۱۸ ثانیه).
6. **اسنپ‌شات ناقص هیچ‌چیز را حذف نمی‌کند** (این یک انتخاب امن است، نه باگ):
   اگر بودجه تمام شود، به‌روزرسانی «خارج‌شده» تا دور بعد عقب می‌افتد.
7. **یک کانال اجباری برای هر گروه.** چندکاناله (فاز ۲ پرامپت) پیاده نشده است؛
   ساختار دیتابیس با `channel_id` در کلید آمادهٔ آن است ولی منطق/فرمان‌ها
   فقط یک کانال را مدیریت می‌کند.
8. **پنل inline (فاز ۳)** پیاده نشده؛ فرمان‌های متنی کامل هستند.
9. **نسخهٔ Bot API رسمی (فاز ۵)** پیاده و آزموده نشده است. Bot API سروش
   دسترسی به فهرست اعضا نمی‌دهد؛ برای آن باید فقط روی رویداد
   `chat_member`/`getChatMember` تکیه کرد.
10. **بدون حساب واقعی آزموده نشده:** رفتار سرور سروش پلاس در این موارد
    شبیه‌سازی/استنتاج از schema است: (الف) ارسال `UpdateChannelParticipant`
    به ادمین (ب) `ChatAdminRequired` روی کانال مخفی (ج) نبود `getAdminLog`
    در سرور (این یکی با schema تأیید شده است). همهٔ این‌ها در تست با
    کلاینت جعلی و آبجکت‌های واقعی کتابخانه پوشش داده شده‌اند، نه با سرور واقعی.
11. **کش تنظیمات عمداً در حافظهٔ پروسه است**؛ چند پروسهٔ هم‌زمان روی یک
    دیتابیس پشتیبانی نمی‌شود (ربات تک‌پروسه است). ری‌استارت، کش را از
    دیتابیس بازسازی می‌کند.
12. مقایسهٔ کارایی با «روش ممنوع» بر پایهٔ تأخیر مصنوعی ۱۲۰ms است؛ عدد
    مطلق تأخیر واقعی سروش اندازه‌گیری نشده — نسبت‌ها معنادار هستند، نه عدد مطلق.

## ۶.۵ عیب‌یابی: «پیام حذف نشد، لینک هم نیامد»

این نشانهٔ **یک** چیز است: وضعیت کاربر «نامعلوم» شده و سیاست fail-safe پیام
را نگه داشته است. سه گام دقیق:

1. **`وضعیت کانال`** را بزنید. اگر خط «⚠️ آخرین خطای بررسی: …» دیده شد،
   همان دلیل است (مثلاً `ChatAdminRequiredError`).
2. روی پیام همان کاربر **ریپلای** کنید و **`تست عضویت`** را بزنید. خروجی
   می‌گوید: منبع `InputPeer`، پاسخ واقعی `getParticipant`، متن خطا و حکم
   نهایی. اگر `منبع InputPeer: unresolved` دیدید یعنی `access_hash` کاربر
   پیدا نشد.
3. لاگ‌ها را ببینید (فایل لاگ در `~/.foxora/logs/`):
   `grep -n "FORCE JOIN" ~/.foxora/logs/*.log | tail -30`
   برچسب‌های مهم: `GATE blocked`، `GATE unknown -> allow`،
   `USER INPUT UNRESOLVED`، `NO ACCESS`، `CHECK ERROR`.

علت‌های شناخته‌شده و رفعشان:

| نشانه | علت | رفع |
|---|---|---|
| `USER INPUT UNRESOLVED` | رویداد/پیام `access_hash` کاربر را نداده بود | در نسخهٔ ۱.۱ زنجیرهٔ لایه‌ای اضافه شد: کش کلاینت → **جست‌وجوی هدفمند در همان گروه (limit=۲۰)** → `get_entity`؛ `access_hash` هم پایدار ذخیره می‌شود. اگر باز هم رخ داد، یک‌بار روی پیام کاربر ریپلای کنید و `تست عضویت` بزنید |
| `NO ACCESS / ChatAdminRequiredError` | حساب ربات در کانال ادمین/عضو نیست یا فهرست اعضا مخفی است | حساب ربات را در کانال **ادمین** کنید (برای رویدادها و `getParticipant`) |
| `FLOOD` | محدودیت نرخ سروش | چند دقیقه صبر؛ سیستم خودش backoff دارد |
| ورود کاربر جدید بی‌اثر بود | در نسخهٔ ۱.۰ آبجکت رویداد به‌جای آبجکت کاربر به پیش‌بررسی می‌رفت و `access_hash` نداشت | در ۱.۱ اصلاح شد (`event.get_user()`)، و `access_hash` رویداد کانال هم ذخیره می‌شود |

> نسخهٔ ۱.۱ همچنین `access_hash` را در هر تأیید موفق در دیتابیس نگه می‌دارد،
> پس «بررسی بعدی = یک فراخوانی» حتی برای کاربری که کلاینت هنوز نمی‌شناسد.

## ۶.۶ یافتهٔ میدانی: `channels.getParticipant` روی سروش **نیست** — و چهار مسیر جایگزین

روی حساب واقعی این پروژه، `channels.getParticipant` همیشه این را برمی‌گرداند:

```
RPCError 422: NOT_SUPPORTED (caused by GetParticipantRequest)
```

یعنی متد در TL Schema هست و کتابخانه هم می‌فرستد، ولی **سرور سروش پیاده
نکرده است**. بنابراین طراحی «یک متد برای بررسی عضویت» غلط بود: هر پیام به
«نامعلوم» می‌رسید و سیاست fail-safe آن را نگه می‌داشت (لینک هم نمی‌آمد).
اصلاح ۱.۲: بررسی عضویت **زنجیره‌ای** شد؛ اولین مسیری که پاسخ قطعی بدهد
برنده است و مسیرهای مرده برای همیشه کنار گذاشته می‌شوند.

| # | مسیر | متد واقعی | حکم «عضو نیست» می‌دهد؟ | هزینه | وضعیت روی سروش |
|---|---|---|---|---|---|
| A | `channels.getParticipant` | `GetParticipantRequest(channel, participant)` | بله (`UserNotParticipant`) | ۱ RPC | ⛔️ `422 NOT_SUPPORTED` (اندازه‌گیری‌شده) |
| B | جست‌وجوی هدفمند عضو | `GetParticipantsRequest(filter=ChannelParticipantsSearch(q), limit≤50)` | **نه** — فقط «پیدا شد» قطعی است | ۱ RPC کوچک | پشتیبانی نامعلوم (وابسته به خواندنی بودن فهرست) |
| C′ | **پیمایش هدفمند** (نسخهٔ ۱.۳) | `GetParticipantsRequest(ChannelParticipantsRecent, offset, limit≤200)` تا پیدا شدنِ همان کاربر | بله، **اگر** پیمایش کامل شود | برای کانال کوچک ≈۱ RPC؛ سقف ۵٬۰۰۰ عضو / ۲۰ ثانیه | ✅ کار می‌کند (فهرست با ۱۶ عضو، یک صفحه) |
| C | اسنپ‌شات کامل + diff | `GetParticipantsRequest(ChannelParticipantsRecent, offset, limit≤200)` | بله، **اگر** اسنپ‌شات کامل و تازه باشد | `⌈N/200⌉` RPC هر بازه | با ادمین بودن یا فهرست باز کار می‌کند |
| D | **روش ربات‌های تلگرامی** | Bot API: `POST https://bot.splus.ir/v2/{token}/getChatMember` با `chat_id`,`user_id` | بله (`left`/`kicked`) | ۱ درخواست HTTP | در `spluslib/bot_client.py:1469` هست؛ پشتیبانی سرور **آزموده نشده** |
| E | رویداد | `UpdateChannelParticipant` | بله (`user_left`/`user_kicked`) | ۰ (فقط ادمین) | کار می‌کند |

نکتهٔ مهم دربارهٔ D: توکن ربات باید **ادمین همان کانال** باشد؛ وگرنه
`no_access` می‌دهد. این همان مسیری است که ربات‌های تلگرامی برای
«عضو اجباری» استفاده می‌کنند (یک درخواست، بدون پیمایش فهرست).

### سنجش یک‌دستوری روی سرور خودتان

بدون `--channel`، همهٔ کانال‌های ثبت‌شده در دیتابیس ربات سنجیده می‌شوند

(هشدار `Unclosed client session` نمی‌ماند).

خروجی، جدول «مسیر → نتیجه» است (`OK` / `NOT_SUPPORTED` / `NO_ACCESS` /
`FLOOD`) و در پایان می‌گوید با این حساب کدام مسیرها قابل استفاده‌اند.
ابزار **فقط می‌خواند** (هیچ حذف/ارسال/تغییر عضویتی ندارد) و باید وقتی ربات
خاموش است اجرا شود (دو پروس با یک session string هم‌زمان کار نمی‌کنند).

### رفتار عملی در هر حالت

| آنچه روی سرور جواب می‌دهد | `sync_mode` | دقت تصمیم | هزینهٔ هر پیام |
|---|---|---|---|
| رویداد + ادمین | `event` | لحظه‌ای | ۰ |
| Bot API `getChatMember` | `bot_api` | لحظه‌ای (۱ HTTP) | ۰ تا زمان انقضای TTL |
| اسنپ‌شات | `snapshot` | تا اندازهٔ `FORCE_JOIN_SNAPSHOT_TRUST` (پیش‌فرض ۲× بازهٔ تازه‌سازی) | ۰ (کش) + بازه‌های تازه‌سازی |
| هیچ‌کدام | `probe` | نامعلوم ⇒ پیام **حذف نمی‌شود** | ۰ |

**پنجرهٔ خطای شناخته‌شدهٔ حالت snapshot:** کاربری که تازه عضو کانال شده و
اسنپ‌شات هنوز تازه‌سازی نشده، ممکن است «غیرعضو» دیده شود. برای همین:
* بازهٔ تازه‌سازی پله‌ای است (`snapshot_interval_for`): تا ۲٬۰۰۰ عضو = ۳۰۰
  ثانیه، تا ۱۰٬۰۰۰ = ۹۰۰ ثانیه، تا ۵۰٬۰۰۰ = ۱ ساعت، بیشتر = ۶ ساعت؛
* حکم «غیرعضو» فقط تا `FORCE_JOIN_SNAPSHOT_TRUST` ثانیه (پیش‌فرض ۶۰۰)
  پذیرفته می‌شود؛ بعد از آن «نامعلوم» است؛
* اسنپ‌شات **ناقص** هرگز حکم «خروج» نمی‌دهد (قرارداد قبلی حفظ شده)؛
* اگر `join_date` کاربر بعد از شروع اسنپ‌شات باشد، «عضو» در نظر گرفته می‌شود.

برای همین روی کانال بزرگ، مسیر D (ربات ادمین + `getChatMember`) توصیهٔ اول
است، بعد C.

### دیده شدن خطا (بدون حذف بی‌شاهد)

* هر شکست در `_record_last_error` ثبت می‌شود و در «وضعیت کانال» و
  «تست عضویت» دیده می‌شود.
* `diagnose` حالا ترتیب مسیرها، نتیجهٔ هر مسیر و «مسیر برنده» را چاپ می‌کند.
* اگر هیچ مسیری نباشد، پیام **حذف نمی‌شود** ولی خطای `no_route` ثبت می‌شود.
* سیاست اختیاری: `FORCE_JOIN_STRICT_UNKNOWN=1` ⇒ در حالت «نامعلوم» پیام
  حذف نمی‌شود ولی راهنمای لینک (با محدودیت نرخ) ارسال می‌شود.

## ۶.۷ «چرا حکم همیشه نامعلوم بود؟» — سه باگ واقعی که در گزارش زندهٔ کانال ۱۶ نفره دیده شد

خروجی واقعی «تست عضویت» روی کانال «Order a website» (۱۶ عضو):

```
مسیرهای سالم: جست‌وجوی هدفمند عضو، اسنپ‌شات کامل اعضا
اسنپ‌شات: کامل، ۱۶ عضو، ۱۸۶۴ ثانیه پیش (اعتبار ۶۰۰ ثانیه)
نتیجهٔ هر مسیر: جست‌وجوی هدفمند عضو=absent، اسنپ‌شات کامل اعضا=snapshot_stale
حکم: نامعلوم (لایه: grace)
```

سه ایراد که هر سه با هم «نامعلوم» می‌ساختند و همه رفع شدند:

| # | باگ | چرا کشنده بود | رفع در ۱.۳ |
|---|---|---|---|
| ۱ | هیچ مسیر **قطعی** وجود نداشت | `getParticipant` روی سروش نیست؛ `absent` در جست‌وجو عمداً غیرقطعی است (فقط صفحهٔ اول)؛ Bot API هم بدون `BOT_TOKEN` در دسترس نیست ⇒ هیچ‌کس نمی‌توانست بگوید «عضو نیست» | مسیر **پیمایش هدفمند** اضافه شد: فهرست تا پیدا شدنِ همان `user_id` خوانده می‌شود؛ برای کانال ۱۶ نفره = **۱ RPC**. «پیدا نشد + پیمایش کامل» = «عضو نیست» → حذف + لینک |
| ۲ | اسنپ‌شات عملاً **همیشه کهنه** بود | بازهٔ تازه‌سازی در حالت `event` = ۱۲ ساعت، ولی اعتبار حکم = ۶۰۰ ثانیه ⇒ در ۹۹٪ زمان `snapshot_stale` | وقتی هیچ مسیر تک‌کاربره‌ای نیست، اسنپ‌شات با بازهٔ کوتاه (۳۰۰ ثانیه برای ≤۲٬۰۰۰ عضو) تازه می‌شود و **اعتبار هم خودکار** از همان بازه حساب می‌شود (`2×بازه+۶۰`) |
| ۳ | کاربر تازه‌وارد **هیچ پیامی** نمی‌گرفت | راهنما فقط پس از حذف پیام ارسال می‌شد؛ تا وقتی حکم «نامعلوم» بود، نه حذفی بود نه لینکی | `notify_join`: به‌محض ورود کاربر به **گروه**، اگر عضویت کانال تأیید نشود، همان لحظه لینک کانال ارسال می‌شود (`FORCE_JOIN_NOTICE_ON_JOIN`، پیش‌فرض روشن) |

ترتیب جدید زنجیره (ارزان‌ترین → گران‌ترین):

```
getParticipant  →  Bot API getChatMember  →  جست‌وجوی هدفمند  →  پیمایش هدفمند  →  اسنپ‌شات
 (روی سروش نیست)      (اگر ربات ادمین باشد)      (فقط «هست»)        (حکم قطعی)        (کمتر تازه)
```

قواعد امنیتی مسیر پیمایش هدفمند (همان قرارداد قبلی، بدون استثنا):

* سقف `FORCE_JOIN_SCAN_MAX_MEMBERS` (پیش‌فرض ۵٬۰۰۰) و بودجهٔ
  `FORCE_JOIN_SCAN_BUDGET` (۲۰ ثانیه، و همیشه کمتر از سقف انتظار مسیر پیام)؛
* cooldown هر کانال `FORCE_JOIN_SCAN_COOLDOWN` (۵ ثانیه) تا یک موج ورود،
  کانال را زیر پیمایش پیاپی نبرد؛
* پیمایش **ناقص** = «نامعلوم»؛ هرگز «غیرعضو». حذف فقط با پیمایش کامل
  (`complete=True`) یا `found`؛
* نتیجهٔ قطعی در SQLite با منبع `scan` و TTL معمول ذخیره می‌شود ⇒ پیام‌های
  بعدی همان کاربر صفر RPC.

### اگر همین حالا خواستید ببینید درست شد

1. `git pull && ./foxora stop && ./foxora`
2. در گروه: `کانال من <لینک کانال>` (ثبت دوباره تا مسیرها سنجیده و ذخیره شوند)
3. `تست عضویت` با ریپلای روی پیام همان کاربر → باید ببینید:
   `مسیرهای سالم: پیمایش هدفمند اعضا، …` و در «نتیجهٔ هر مسیر»
   `پیمایش هدفمند اعضا=absent` و حکم **غیرعضو** → حذف + لینک.

> نکتهٔ صادقانه: اگر کاربر **واقعاً** عضو کانال باشد و ادمین کانال هم نباشید،
> ممکن است فهرست اعضا برای حساب شما محدود باشد؛ در آن حالت مسیر
> `no_access` می‌دهد و حکم «نامعلوم» می‌ماند (fail-safe) — بهترین رفع:
> ربات رسمی را ادمین کانال کنید (`getChatMember`) یا حساب را ادمین کانال کنید.

## ۶.۸ «راهنما آمد، اما بعد از عضویت هیچ تأییدی نیامد» — صف تأیید عضویت

گزارش زندهٔ کاربر: پیام «ارسال پیام فقط برای اعضای کانال…» با لینک آمد ✅،
کاربر عضو کانال شد، ولی هیچ پیامی مبنی بر «عضویت تأیید شد» نیامد و بررسی
هم ادامه پیدا نکرد.

ریشه: اعلامِ «عضو شد» در MTProto با `UpdateChannelParticipant` می‌آید و این
آپدیت **فقط برای ادمین‌های کانال** فرستاده می‌شود. حساب ربات ادمین کانال
نیست ⇒ سرور هیچ خبری نمی‌دهد ⇒ نه «تأیید شد»ی بود و نه باطل‌شدن کش.

راه‌حل (نسخهٔ ۱.۴) — صف انتظار تأیید:

1. هر جا راهنمای لینک فرستاده شود (ورود به گروه یا حذف پیام)، کاربر با
   زمان ورود در صف `_awaiting_confirm` ثبت می‌شود.
2. `confirm_watcher` هر ۱۰ ثانیه صف را می‌بیند و برای هر کاربر
   **بررسی تازه** (`force=True`، بدون کش) انجام می‌دهد؛ اولین بررسی ~۱۲
   ثانیه بعد، سپس با عقب‌اندازی نمایی، تا سقف
   `FORCE_JOIN_CONFIRM_WINDOW` (پیش‌فرض ۳۰ دقیقه) و
   `FORCE_JOIN_CONFIRM_MAX_CHECKS` (۲۰ بار).
3. به‌محض اینکه کاربر در فهرست اعضا دیده شود، پیام زیر در گروه ارسال
   می‌شود و کاربر از صف حذف می‌شود:

   ```
   ✅ عضویت شما در کانال تأیید شد.
   📢 کانال: …
   از این پس پیام‌هایتان در گروه ارسال می‌شود.
   ```
4. سه مسیر دیگر هم همان تأیید را فوری می‌فرستند:
   * **رویداد** ورود به کانال (اگر حساب ادمین باشد)؛
   * **پیام بعدی همان کاربر** بعد از عضویت (درِ عضویت او را آزاد می‌کند و
     تأیید را می‌فرستد)؛
   * مسیر Bot API `getChatMember` اگر فعال باشد.

نکتهٔ فنی مهم: `resolve_status` حالا پارامتر `force=True` دارد. بدون آن،
حکم «غیرعضو» تا ۳۰۰ ثانیه در کش می‌ماند و کاربری که همین حالا عضو شده
تأیید نمی‌گرفت (همین باگ در تست `test_confirmation_is_sent_as_soon_as_membership_is_confirmed`
قابل بازتولید بود). «تست عضویت» هم با `force=True` اجرا می‌شود تا همیشه
حقیقتِ همین لحظه را بگوید.

> وضعیت: منطق صف و سه مسیر تأیید با تست‌های آفلاین آزموده شده
> (`test_join_notice_puts_user_in_confirmation_queue`،
> `test_confirmation_is_sent_as_soon_as_membership_is_confirmed`،
> `test_no_confirmation_while_user_is_still_not_member`،
> `test_confirmation_queue_expires_without_spam`،
> `test_member_message_after_joining_sends_confirmation`،
> `test_channel_join_event_confirms_immediately`). اجرای زندهٔ آن روی سرور
> سروش **آزموده نشده** (این محیط دسترسی شبکه ندارد).

## ۶.۹ قالب پیام‌ها و راهنمای کاربر (نسخهٔ ۱.۵)

### بلوک جدید «راهنمای روباه» (در «لیست ادمینی»)

در ابتدای فهرست دستورات ادمین، این بلوک اضافه شد — عنوان Bold و **هر دو
دستور Bold داخل یک نقل‌قول** سروش پلاس (نه دو نقل‌قول جدا):

```
📣 اضافه کردن کانال من برای عضویت اجباری دستور
راهنمای کانال
راهنمای اجرا
```

* `📣 اضافه کردن کانال من برای عضویت اجباری دستور` → `MessageEntityBold`
* `راهنمای کانال` و `راهنمای اجرا` → هر کدام `MessageEntityBold` و کل
  دو خط در **یک** `MessageEntityBlockquote`.
* offset ها با UTF-16 حساب می‌شوند (`_u16`)؛ متن و entity همیشه از یک
  تابع ساخته می‌شوند تا از هم جدا نیفتند (`modules/admin_help_builder.py`).

### «راهنمای کانال»

```
راهنمای دستورات کانال من

» کانال من
این دستور کانال رو به لیست خودش اضافه می‌کنه، اول باید کانال عمومی باشه. به این صورت مثلا « کانال من @euwoq »

» تنظیم عضویت اجباری
برای فعال کردن عضویت اجباری

» لغو عضویت اجباری
برای خاموش کردن قابلیت

» تست عضویت
برای اینکه تست کنید یک کاربر عضو شده یا نه
```

نام چهار دستور Bold است. این متن برای **همه** قابل خواندن است (حتی غیرعضو).

### «راهنمای اجرا»

کل متن Bold است، ولی خط‌های پشتیبانی و مثال داخل نقل‌قول:

```
قابلیت کانال من برای عضویت اجباری کاربری می‌باشد که تازه عضو گروه شده…

ربات پشتیبانی : @aifox_bot          ← Bold + Blockquote

… و دستور کانال من رو می‌نویسید به روش آیدی کانال

مثال

کانال من @ai_fox                    ← Bold + Blockquote
```

### پیام «عضو نیست شوید» (راهنما)

```
کاربر : @osien                      ← Blockquote
ارسال پیام در این گروه مجاز نیست، اول عضو کانال زیر شوید
📢 لینک کانال : https://splus.ir/Orderawebsite
بعد از تایید عضویت میتوانید پیام بدهید
```

نام کاربر: اول **یوزرنیم** (`@…`)، اگر نداشت **نام نمایشی**، و اگر آن هم
نبود شناسهٔ عددی (`user_label`).

### پیام تأیید عضویت

```
💌 کاربر : @osien                   ← Blockquote
عضو کانال شد، میتوانید پیام ارسال کنید   ← Bold
```

### پیام ثبت کانال (فقط چهار خط)

```
✅ کانال اجباری ثبت شد.
📢 Order a website
🔗 https://splus.ir/Orderawebsite

👥 تعداد اعضای کانال: ۱۷
```

حالت همگام‌سازی و «مسیرهای تأییدشده» از پیام موفق حذف شدند (در لاگ و در
«تست عضویت»/«تشخیص عضویت» هستند). فقط اگر قابلیت **فعال نشد**، دلیل‌ها به
مالک گفته می‌شود؛ موفقیت هیچ‌وقت با ادعای اضافی همراه نمی‌شود.

### «تست عضویت» = یک جمله

| فرمان | خروجی |
|---|---|
| `تست عضویت` (با ریپلای یا آیدی/یوزرنیم) | `کاربر در کانال عضو هست` / `کاربر در کانال عضو نیست` / `وضعیت عضویت این کاربر مشخص نشد.` |
| `تشخیص عضویت` یا `تست عضویت کانال` | گزارش کامل فنی (مسیرها، نتیجهٔ هر مسیر، خطا، منبع `InputPeer`) |

> وضعیت: همهٔ موارد بالا با تست‌های آفلاین آزموده شده‌اند (متن‌ها،
> `MessageEntity` ها با offset درست UTF-16، و مسیر فرمان در هندلر). قالب
> نهایی روی اپ سروش پلاس **آزموده نشده** (این محیط به اپ دسترسی ندارد)؛
> اگر جایی Bold یا نقل‌قول درست دیده نشد، بگویید تا offset/entity عوض شود.

## ۶.۱۰ سرعت تأیید عضویت + تضمین «ربات هیچ‌وقت کند نمی‌شود» (نسخهٔ ۱.۶)

### سرعت تأیید

قبلاً تأیید عضویت تا ۱۲ تا ۲۲ ثانیه طول می‌کشید (اولین بررسی ۱۲ ثانیه و
چرخهٔ ناظر ۱۰ ثانیه). حالا:

| سنجه | قبل | حالا |
|---|---|---|
| اولین بررسی بعد از ارسال راهنما | ۱۲ ثانیه | **۳ ثانیه** |
| چرخهٔ ناظر تأیید | ۱۰ ثانیه | **۲ ثانیه** |
| تأخیر عملی تا «عضویت تأیید شد» | ~۱۲–۲۲ ثانیه | **~۳–۵ ثانیه** |
| پیمایش برای n کاربرِ در انتظار | n پیمایش | **۱ پیمایش مشترک** |

سه تغییر این را ساخت:

1. **زمان‌بندی تهاجمی‌تر**: اولین تلاش ۳ ثانیه، بعد ۴، ۶، ۸، ۱۲، ۲۰…
   (`_CONFIRM_BACKOFF`) تا سقف پنجره.
2. **پاس مشترک هر کانال**: همهٔ منتظرانِ یک کانال با **یک** پیمایش
   (`api.find_members`) بررسی می‌شوند؛ ۱۰ کاربر هم‌زمان = همان یک RPC.
3. **اولویت Bot API**: اگر `BOT_TOKEN` تنظیم باشد، `getChatMember` هر کاربر
   یک درخواست HTTP است (بدون فهرست) و همان مسیر سریع‌تر جواب می‌دهد.

مسیرهای فوری دیگر که تغییری نکردند: رویداد `UpdateChannelParticipant`
(اگر ادمین کانال باشید، همان لحظه) و **پیام بعدی همان کاربر** (دروازه
عضویت او را آزاد می‌کند و تأیید را می‌فرستد).

### تضمین کارایی — چهار ترمز سخت

| ترمز | مقدار پیش‌فرض | چه چیزی را تضمین می‌کند |
|---|---|---|
| `FORCE_JOIN_GATE_TIMEOUT` | ۳ ثانیه | هر تصمیم مسیر پیام حداکثر ۳ ثانیه (وگرنه fail-safe: پیام می‌ماند) |
| `FORCE_JOIN_GATE_SCAN_BUDGET` | ۱٫۵ ثانیه | پیمایش در مسیر پیام هرگز بیشتر از این طول نمی‌کشد |
| `FORCE_JOIN_GATE_SCAN_MAX_MEMBERS` | ۳۰۰۰ | کانال بزرگ‌تر هرگز در مسیر پیام پیمایش نمی‌شود؛ می‌رود پس‌زمینه |
| `FORCE_JOIN_RPC_PER_MINUTE` | ۱۲۰ | سهمیهٔ **مستقل** RPC این ماژول در دقیقه؛ تمام شود ⇒ هیچ بررسی‌ای انجام نمی‌شود (نامعلوم، بدون حذف) |

به‌علاوه:

* همهٔ کارهای سنگین (پیمایش، اسنپ‌شات، تأیید) در **task جدا** و پشت
  `asyncio.Semaphore` (`FORCE_JOIN_MAX_CONCURRENCY`، پیش‌فرض ۲) اجرا
  می‌شوند؛ مسیر پیام هرگز منتظرشان نمی‌ماند.
* مسیر گرم (کاربری که وضعیتش در کش است) **صفر** RPC دارد: بنچمارک
  ۳۰۰ پیام → ۰ فراخوانی، میانگین ۰٫۰۷۶ms.
* ناظرها هرگز در حلقهٔ پیام نیستند و بین کارها `await sleep` می‌دهند.

> وضعیت: زمان‌بندی، بودجه و مسیرها با تست‌های آفلاین آزموده شده‌اند
> (`test_confirmation_timing_is_fast`،
> `test_confirmation_batches_all_waiting_users_in_one_scan`،
> `test_rpc_budget_protects_the_bot`،
> `test_inline_scan_never_runs_for_big_channels`،
> `test_gate_uses_short_timeout_not_the_long_budget`). عدد دقیق تأخیر روی
> سرور سروش **آزموده نشده** (به RTT سرور وابسته است).

## ۶.۱۱ تخلف‌کار هرگز «اول عضو کانال شوید» نمی‌شنود

اگر پیام کاربر **تخلف** باشد، عضویت اجباری کنار می‌رود و مسیر عادی مجازات
(اخطار / سکوت / اخراج طبق «تغییر مجازات» گروه) اجرا می‌شود. برای چنین
کاربری نه پیام راهنمای عضویت فرستاده می‌شود و نه پیامش به‌عنوان «غیرعضو»
حذف می‌شود.

دلیل: این کاربران اغلب ربات‌های تبلیغاتی‌اند؛ فرستادن لینک کانال برایشان
هم بی‌فایده است، هم گروه را شلوغ می‌کند و هم مجازاتشان را عقب می‌اندازد.

شش سنجه‌ای که «تخلف» را تشخیص می‌دهند (همه محلی و بدون RPC):

| سنجه | تشخیص با | برچسب لاگ |
|---|---|---|
| نام تبلیغاتی کاربر | `ad_name_detector.reason(sender)` | `ad_name` |
| نام فیلترشدهٔ گروه | `group_names_storage.find_matching_filtered_name` | `filtered_name` |
| کلمهٔ فیلترشدهٔ گروه | `group_words_storage.find_matching_filter_word` | `filter_word` |
| کلمهٔ ممنوعه (حالت سخت‌گیرانه) | `spam_detector.check_banned_words` | `banned_word` |
| متن تبلیغاتی/آگهی | `big_spam.looks_promotional` | `promotional` |
| بن/سکوت از قبل | `banned_storage.is_banned` + `user_tracker.is_muted` | `banned` / `muted` |

نکته‌ها:

* بررسی فقط برای کاربری انجام می‌شود که **غیرعضو** تشخیص داده شده؛ برای
  اعضا و ادمین‌ها هیچ هزینه‌ای ندارد.
* خروجی `False` (اجازه) است، پس اگر هیچ ماژول تنبیهی هم واکنش نداد، بدترین
  حالت «پیام پاک نشده» است — هرگز حذف بی‌شاهد.
* در لاگ: `FORCE JOIN GATE deferred to moderation ... reason=…`
  و شمارندهٔ `STATS["deferred"]`.
