# 🧬 «پاکسازی کامل» — طراحی و محدودیت‌های واقعی

قابلیت جدیدی که با دستور `پاکسازی کامل` همهٔ پیام‌های **قابل‌حذفِ** یک گروه را
تا آخر پاک می‌کند و پیام وضعیت را به‌صورت زنده ویرایش می‌کند.

## ساختار

```
modules/full_purge/
    __init__.py   صادرکنندهٔ سه بخش
    texts.py      قالب‌های Bold/نقل‌قول سروش پلاس (بدون مارک‌داون)
    core.py       موتور خالص: صفحه‌بندی، حذف دسته‌ای، Retry/Backoff، وضعیت
    service.py    جریان دستور: مجوز → تأیید → قفل → اجرا → آزادسازی
tests/test_full_purge.py     ۱۱۸ بررسی (۷ تا ۴۲۰۰ پیام، خطاها، هم‌زمانی، قفل)
```

## محدودیت‌های واقعیِ API (بررسی‌شده روی splusthon 1.1.4)

| موضوع | واقعیت | تصمیم در کد |
|---|---|---|
| `client.get_messages(entity, limit=n, max_id=…)` | `limit` فقط ظرفیتِ هر **درخواست** است | `PAGE_SIZE = 100` و صفحه‌بندی با `max_id` (جدید → قدیم) |
| `client.delete_messages(entity, ids)` | یک RPC؛ سرور سروش بیش از ۱۰۰ شناسه را رد می‌کند | `BATCH_SIZE = 100` |
| حذف پیامِ از قبل حذف‌شده | خطا نمی‌دهد (بی‌اثر) | شمارنده فقط حذف‌های **موفقِ** RPC را می‌شمارد |
| `iter_messages` | یک‌بارمصرف و بدون کنترلِ بین دسته‌ها | استفاده نمی‌شود؛ حلقهٔ `max_id` جایش را گرفته |
| تاریخچهٔ مخفی/بدون دسترسی | `get_messages` خطا می‌دهد | `reason=history_unavailable` و **ادعای پاکسازی نمی‌کنیم** |
| FloodWait | با `.seconds` | انتظار ≤ ۶۰ ثانیه و تلاش دوباره؛ بلندتر → آن دسته رها و در پایان دوباره تلاش |
| ویرایش پیام | `client.edit_message(msg, text, formatting_entities=…)` | همان پیام؛ خطای ویرایش هرگز پاکسازی را متوقف نمی‌کند |

> **سقفِ مصنوعی وجود ندارد.** شرط پایانِ حلقه فقط «صفحهٔ خالی» است
> (`MAX_PAGES = 100000` تنها نگهبانِ حلقهٔ بی‌نهایت در بدترین حالت است، نه سقفِ
> تعداد پیام). تست، ۷، ۷۵۰، ۴۲۰۰ و **۳۰٬۰۰۰** پیام را کامل پاک می‌کند.

## دستهٔ «رد‌شده» = پیامِ خراب، نه پایانِ کار (رفعِ باگِ «۲۰ پیام ماند»)

سرور سروش اگر **حتی یک** شناسهٔ دسته مشکل داشته باشد (پیامِ خدماتی، شناسهٔ
ناشناخته، پیامی که ربات اجازهٔ حذفش را ندارد)، ممکن است کلِ درخواستِ ۱۰۰تایی را
با خطا برگرداند. نسخهٔ اول همان خطا را «همه حذف شدند» فرض می‌کرد؛ نتیجه: کلِ آن
دسته بی‌صدا جا می‌ماند.

الان:

1. `_delete_with_retry` دسته را با backoff دوباره می‌فرستد.
2. اگر خطا از نوعِ «شناسهٔ بد» بود، `delete_batch` دسته را **نصف** می‌کند و
   بازگشتی ادامه می‌دهد تا فقط شناسهٔ خراب جدا شود (`_partition` سابق حذف شد).
3. هر شناسهٔ جدا‌شده تک‌تک هم امتحان می‌شود؛ تنها شناسه‌ای که واقعاً رد شود در
   فهرستِ `undeliverable` می‌نشیند.
4. `RETRY_ROUNDS = 3` بار برای بازمانده‌ها تلاش دوباره می‌شود.
5. در پایان `VERIFY_ROUNDS = 2` بار تاریخچه **از نو خوانده می‌شود**؛ هرچه مانده
   بود حذف می‌شود (پیام‌هایی که وسطِ کار رسیده‌اند هم همین‌جا گرفته می‌شوند)، و
   آن‌چه واقعاً حذف‌نشدنی بود در پیامِ پایانی صریح گزارش می‌شود
   (`⚠️ پاکسازی کامل انجام شد` + «قابل‌حذف نبود : N»).

## پیامِ خودمان هرگز حذف نمی‌شود

ترتیبِ کار (باگِ «پیام وضعیت خودش را پاک می‌کرد»):

1. اول پیامِ **قالب ۲** («آغاز پاکسازی خودکار») فرستاده می‌شود،
2. شناسهٔ همان پیام + شناسهٔ پیامِ «پاکسازی کامل» + شناسهٔ پیامِ «تایید» در
   `protect_ids` می‌نشیند،
3. بعد قفل و بعد حذف.

`core.run(protect_ids=…)` این شناسه‌ها را **قبل از هر RPC** از هر دسته فیلتر
می‌کند، پس حتی اگر همان پیام در صفحهٔ تاریخچه دیده شود حذف نمی‌شود.

## هم‌زمانی و صف

* صفِ اختصاصی: `_ACTIVE` در `core.py` — کلید = `chat_id`، مقدار = وضعیتِ همان گروه.
* قفلِ per-chat با `is_running()`؛ اجرای دوم در همان گروه `already_running` می‌گیرد.
* هر گروه تسکِ مستقل خودش را دارد (`full-purge:<chat_id>`)، پس دو گروه هم‌زمان
  بدون هیچ تداخلی کار می‌کنند (تست ۶).
* هیچ‌کدام از `message_delete_queue`، `fair_delete_queue`، `moderation_queue` و
  «پاک عدد» استفاده **یا** تغییر نشده‌اند (تست ۱۰ این را از روی سورس می‌سنجد).

## قفلِ گروه

* با همان سیستم موجود: `bot.group_actions.lock_group()` /
  `unlock_group()` (همان دستورهای «قفل»/«باز»، با snapshot وضعیت قبلی).
* آزادسازی در `finally` انجام می‌شود: خطای حذف، خطای ویرایش، لغو یا استثنا هم
  گروه را قفل نمی‌گذارد. اگر خودِ قفل شکست، پاکسازی ادامه می‌یابد و
  `unlock` بی‌مورد صدا زده نمی‌شود.

## پیام وضعیت

* یک پیام؛ همان ویرایش می‌شود (تست ۸: هیچ پیام جدیدی برای هر دسته ساخته نمی‌شود).
* ویرایشِ هوشمند: حداقل ۲ ثانیه فاصله **و** حداقل ۲۵ حذفِ تازه، و همیشه
  «متنِ عوض‌شده» — پس ویرایشِ تکراری رخ نمی‌دهد.
* بعد از ۳ خطای ویرایش، ویرایش کنار گذاشته می‌شود و پاکسازی ادامه می‌یابد.
* زمانِ خوانا: «۲ ثانیه»، «۱ دقیقه و ۲۰ ثانیه»، «۲ دقیقه»، «۱ ساعت و ۵ دقیقه».

## قالب‌بندی

* `MessageEntityBold` + `MessageEntityBlockquote` با آفستِ **UTF-16**؛ هیچ
  مارک‌داون/`parse_mode`ای در کار نیست.
* کتابخانه `MessageEntityUnderline` دارد (`UNDERLINE_SUPPORTED = True`) ولی در
  قالب‌های کارفرما زیرخط خواسته نشده؛ هیچ چیزِ جعلی هم ساخته نشده.
* قالب ۱ (تأیید) و قالب ۲ (وضعیت) دقیقاً از روی تصویر کارفرما.

## اجرا روی ترموکس

```bash
cd ~/Foxora.ai
python3 tests/test_full_purge.py            # ۱۴۸ بررسی، بدون شبکه
```

داخل گروه (فقط مالک/ادمینِ ثبت‌شده):

1. بنویس `پاکسازی کامل` → پیامِ تأیید (قالب ۱)
2. `تایید` → قفل گروه + پیام وضعیت (قالب ۲) که زنده ویرایش می‌شود
3. پایان → شمارش نهایی، مدت زمان، «قفل گروه به حالت قبل برگشت»

`لغو` در مرحلهٔ تأیید، هیچ کاری نمی‌کند و گروه دست‌نخورده می‌ماند.
